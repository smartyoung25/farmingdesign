# 작업지시서 WO-018: 사업장 한 곳 — 기입 7단계를 레일 하나로

- 작성일: 2026-10-02
- 작업 유형: 리팩터링
- 선행 지시서: 없음

## 1. 목적
- 한 사업장의 상태가 **두 화면에 흩어져 있다**. 기입 허브와 케이스 상세가 같은 7단계를 각자 내고 서로를 앵커로 가리킨다.
- 사용 안내에 등재된 `/entry*` 화면이 **아홉**이다. 하나를 채우려고 아홉 중 어디로 가야 하는지 사용자가 판단해야 한다. 사업장 한 곳 화면의 **레일**로 모은다.

## 2. 배경·사용자
- 사용자 지시(2026-10-02): *「흐름을 세부적으로 연계하고」* · ★사용자 결정 2026-10-02: 전면(21→9)
- 실측(`python measure_console_ia.py`): 기입이 흩어진 화면 **9개**(M7). 기입 허브의 링크 열한 개 중 **셋이 케이스 상세의 앵커로 되돌아간다**.
- 실측: 새 케이스 화면의 보이는 입력 칸이 **46개**다. 한 번에 한 칸씩 거부되는 흐름을 에이전트가 보고했다(재측정 전).
- 사용자: 사업장을 가진 사람 — 한 번에 다 채우지 않고 자료가 생길 때마다 돌아온다. 그래서 **어디까지 했는지**가 화면의 중심이어야 한다.

## 3. 범위
- 포함: 사업장 한 곳 화면의 7단계 레일 · 기입 폼 여섯을 그 레일의 칸으로 · 새 케이스를 「새 사업장 만들기」 모드로 · 견적 둘을 도구층 경로로 · 가드 · 뮤테이션
- 제외: **46칸을 줄이는 것** — 어느 칸이 필수인지는 케이스 스키마가 정하고, 줄이면 저장되는 값이 바뀐다. 입력 칸 수는 이 차수의 지표가 아니다
- 제외: **거부 메시지를 한 번에 모아 보이는 것** — 먼저 재서 몇 건인지 확인한 뒤 별도로 다룬다
- 제외: **저장·재생성 동작 변경** — `POST` 경로의 입출력을 바꾸지 않는다
- 제외: **홈 재배치**(WO-016) · **안내 화면 해체**(WO-019) · **날것 마크다운**(WO-020)

## 4. 입력·출력
- 입력(전부 기존 구조): `ENTRY_STEPS`(7단계) · 케이스 파일 · 기존 `POST` 경로의 입출력
- 출력: 사업장 한 곳 화면 — 7단계 레일 · 각 칸의 상태 · 그 칸의 폼. 등재되는 `/entry*` 화면은 남지 않는다
- 지표: M7 `9 → 0`

## 5. 기술 조건
- **`POST` 경로의 입출력을 바꾸지 않는다** — 저장되는 값이 바뀌면 케이스 데이터 차수가 되고 추적성 감사를 함께 돌려야 한다.
- **단계 순서를 `ENTRY_STEPS`에서 읽는다** — 화면에 순서를 적지 않는다. 적으면 두 갈래가 된다.
- **계산하지 않는다** — 레일의 상태는 항목 건수 집계와 파일 유무뿐이다(1절 258차 단서).
- **tombstone 케이스를 되살리지 않는다** — 0바이트 케이스는 설계된 묘비다(「손대지 말 것」).
- 견적 둘은 **경로만 도구층으로** 옮긴다 — 편집 동작은 건드리지 않는다.

## 6. 작업 단위 (순서대로)
- T1: 7단계 레일 — 완료 조건: 단계 이름·순서가 `ENTRY_STEPS`와 한 건도 다르지 않다
- T2: 기입 폼 여섯을 레일의 칸으로 · 허브의 되돌아가는 앵커 제거 — 완료 조건: 같은 상태를 내는 화면이 하나다
- T3: 새 케이스를 「새 사업장 만들기」 모드로 — 완료 조건: `POST` 입출력이 착수 전과 같다
- T4: 견적 둘을 도구층 경로로 — 완료 조건: 두 화면이 200이고 편집 동작이 착수 전과 같다
- T5: 가드 + 뮤테이션 + 차수 기록 + PRD 표 갱신 — 완료 조건: 7절 전부 통과

## 7. 수용기준
- [ ] 레일의 단계 이름·순서를 `ENTRY_STEPS`에서 **다시 읽어** 화면과 일치한다 (확인: `python -m pytest test_webapp.py -q -k 298cha`)
- [ ] 등재되는 `/entry*` 화면이 **0개**다 — M7이 0이다 (확인: `python measure_console_ia.py`)
- [ ] 같은 7단계 상태를 내는 화면이 **하나**다 (확인: `python -m pytest test_webapp.py -q -k 298cha`)
- [ ] 여섯 폼의 `POST` 입출력이 착수 전과 같다 — 저장되는 키와 값의 종류가 바뀌지 않았다 (확인: 같은 명령)
- [ ] 케이스 JSON이 한 바이트도 바뀌지 않았다 (확인: `python audit_traceability.py`)
- [ ] 0바이트 케이스가 그대로 0바이트다 (확인: `python -m pytest test_cases.py -q`)

## 8. 제약·주의사항
- 🔴 **저장 동작을 건드리면 데이터 차수가 된다.** 이 차수는 화면 배치만 바꾼다 — 추적성 감사가 착수 전과 같은 결과를 내야 한다.
- 🔴 **입력 칸 46개를 이 차수에 줄이지 않는다.** 어느 칸을 뺄지는 케이스 스키마의 판단이고, 줄이면 저장되는 값이 달라진다.
- 🔴 **어느 단계를 먼저 하라고 하지 않는다.** 레일은 순서를 보일 뿐 다음 할 일을 고르지 않는다.
- ⚠️ 기입 허브를 없애면 그 화면을 단정하던 가드가 움직인다. 지우지 말고 레일 가드로 옮긴다.
- ⚠️ 한 번에 한 칸씩 거부되는 흐름은 **에이전트 보고이고 아직 재지 않았다** — 이 차수의 지표가 아니다.

- `POST` 입출력이 같다는 것을 **무엇으로 확인했는지** 적는다. 「바꾸지 않았다」는 서술만으로는 검산되지 않는다.
