## 시작하기 전에 — 사례 전체를 관통하는 한 문장

Anthropic 사내 10개 팀, 기업 도입 7곳, 한국어권 후기 28건을 훑고 나서 남는 결론은 하나였습니다.

> **성과가 좋은 곳은 예외 없이 '검증 루프'를 붙였고, 성과를 부풀린 곳은 예외 없이 그것이 없었습니다.**

Rakuten의 7시간 자율 코딩도, Ladybird의 Rust 2만 5천 줄 포팅도, 컬리의 데일리 브리핑도 전부 "Claude가 스스로 돌려볼 수 있는 검사"를 갖고 있었습니다. 반대로 Anthropic 사내 자동 유지보수 봇의 **머지율은 46%**입니다 — 절반 이상이 버려집니다. Claude Code 제작자 본인도 병렬 세션의 **10~20%는 폐기**한다고 밝혔습니다.

그러니 이 문서를 읽는 방식은 이렇습니다. **"몇 배 빨라졌다"는 숫자보다, 그 팀이 무엇을 검증 수단으로 삼았는지를 보세요.** 그게 복제 가능한 부분입니다.

두 번째 관통선도 미리 말씀드립니다. **시간은 실제로 줄지만 병목이 이동합니다.** 작성 시간이 줄어든 자리에 리뷰 시간이 들어옵니다. 어느 1인 SaaS 운영자의 1년 후기는 이렇게 끝납니다 — *"결국 내 독해 속도가 유일한 병목이 된다."* 사내 도입 후기에서도 *"코드 리뷰가 팀의 바틀넥이 됨"*이 나옵니다. 도입 계획을 세울 때 이걸 계산에 넣지 않으면 3개월 뒤에 당황합니다.

# 제1부. 검증된 사례 — 무엇을, 어떻게, 얼마나

## 1-1. 문서·기획 업무 (이암허브 실무에 가장 가까운 것들)

| 사례 | 무엇을 | 어떻게 (핵심 설계) | 결과 |
|---|---|---|---|
| **상담보고서 자동화** (개인) | 부부상담 10회기 종결보고서, 상담일지, 강의 9명 요약, 메일 발송 | 자료를 Obsidian·VS Code에 미리 쌓아두고 "무엇을 보여주면 되냐"를 **Claude에게 먼저 물음** | 총 **9시간 10분 → 1시간 52분 (80%)** |
| **논문 메타분석** (데이터사이언스) | 논문에서 효과크기·표준편차 추출, Forest/Funnel plot | 커스텀 스킬로 고정. SD 없으면 SE·CI·IQR에서 자동 변환하는 규칙을 스킬에 내장 | 논문 1편당 **30~60분 → 2~3분** |
| **강의 준비** (비개발자) | 영문 교재 번역 → PPT → 강의 스크립트 | 3단계를 각각 자동화하고 **앞 단계 출력을 뒷 단계 입력으로** 연결 | 회당 **5~8시간 → 25분** |
| **뉴스레터** (기획자) | 초안 기획 + 자료 정리 | What·Why·How로 분해한 "설계서"를 먼저 작성 | 주당 **5시간 → 10분** |
| **사규 문서 세트** (실무자) | 사규 30종·부칙 50종·양식 100종 | 역할별 MD 파일(총괄/작성/감수/심사)을 정의해 병렬 처리 | **1시간 내** 생성, 용어 일관성 유지 |
| **거래명세서 → ERP** (유통업) | 매입 명세서 이미지 → JSON → ERP 입력 | 이미지 분석 결과를 **JSON 스키마로 고정**하고 제품 매핑 테이블을 함께 전달 | **3시간 → 1시간**, 정확도 95%+ |

**이 여섯 사례의 공통 설계 세 가지**

1. **입력을 먼저 정리했습니다.** 자료를 폴더에 모으고 나서 시켰지, 대화 중에 하나씩 붙여넣지 않았습니다.
2. **출력 형식을 미리 못 박았습니다.** JSON 스키마, 보고서 목차, 시트 구성 — 형식이 고정되면 검증이 쉬워집니다.
3. **한 번 성공한 절차를 스킬로 굳혔습니다.** 논문 사례의 결론이 특히 인상적입니다 — *"SKILL.md 설계가 성능의 80%"*.

## 1-2. Anthropic 사내 팀 (공식 문서 기준)

가장 참고할 만한 것은 **비개발 직군**의 사례입니다.

**Growth Marketing — 광고 카피 2시간 → 15분, 크리에이티브 산출량 10배**
수백 개 기존 광고의 성과 지표가 담긴 CSV를 넣고 저성과 광고를 식별한 뒤, 글자수 제한 안에서 변형을 생성합니다. 핵심은 **헤드라인 담당과 디스크립션 담당 서브에이전트를 나눈 것**입니다. 한 에이전트가 둘 다 하면 톤이 섞입니다. Figma 플러그인으로 100개 변형을 0.5초에 생성합니다.

**Product Design — 코드베이스 전반의 문구 교체를 1주일 → 30분 통화 2번**
디자이너가 목업 이미지를 그대로 붙여넣어(Command+V) 동작하는 코드를 받습니다. 근무 시간의 80%를 Figma와 Claude Code를 동시에 띄워놓고 씁니다.

**Legal — 발화가 어려운 가족을 위한 예측 텍스트 앱을 1시간에 제작**
주목할 점은 순서입니다. **Claude.ai(Chat)에서 충분히 기획한 뒤 Claude Code로 옮겼습니다.** 라이브러리의 `E-01`(인터뷰 → SPEC → 새 세션)과 정확히 같은 구조입니다.

**Data Science — JS/TS 경험 거의 없이 5,000줄 React 대시보드**
방법론이 재미있습니다. 이른바 **"슬롯머신 방식"** — 상태를 커밋해두고, 30분 자율 실행시키고, 결과를 수락하거나 통째로 버리고 새로 시작합니다. 고쳐 쓰지 않습니다. 라이브러리 `F-01`(2회 교정 규칙)의 극단적 실천입니다.

**Data Infrastructure — 장애 대응 중 20분 절약**
Kubernetes 대시보드 **스크린샷을 그대로 붙여넣어** Pod IP 고갈을 진단했습니다. 텍스트로 옮겨 적지 않았습니다.

| Business Development | 인바운드 응대, 야간 계정 리서치 | 응대 준비 **하루 5시간 → 초안 검토**, 1인당 100개 이상 계정 관리 |

Finance 팀의 한 가지 디테일이 값어치 있습니다. 알림에 지표만 넣지 않고 **맥락을 붙였습니다** — "매출 3% 하락"이 아니라 *"revenue down 3% driven by a dip in APAC enterprise renewals"*. 숫자만 오는 알림은 사람이 결국 다시 파봐야 합니다.

Legal 팀은 사내 법무 플러그인을 **하루 오후 만에** 만들었습니다. 사용 방식은 이렇게 단순합니다 — *"here's our policy folder, draft this launch review"*.

**참고 데이터**: 2026년 5월 Cowork 세션 120만 건 분석 결과, 비즈니스 프로세스·운영이 **33.4%**로 1위, 콘텐츠 작성 16.4%, 소프트웨어 개발은 8.7%에 그쳤습니다. 공식 요약은 이렇습니다 — *"전체 사용의 대략 절반이 '일 주변의 일(the work around the work)'이다."* Cowork는 개발 도구가 아니라 **사무 업무 도구**로 쓰이고 있습니다.

# 제2부. 실패 사례 — 이쪽이 더 값어치 있습니다

성공 사례는 따라 하기 어렵지만, 실패 사례는 **오늘 바로 피할 수 있습니다.**

## 2-1. Anthropic이 스스로 공개한 한계

**① 사내 자동 유지보수 봇 — 머지율 46%**
iOS·Android·데스크톱·웹·CLI에 걸쳐 12개 유지보수 루틴(크래시 퍼징, 데드코드 제거, flaky 테스트 수정)을 매일 돌린 결과, **PR 388건 중 180건만 머지**됐습니다. 절반 이상이 폐기입니다. Claude Code 제작자 본인은 이를 *"early signs of life"*라고 표현했습니다 — 아직 실험 단계라는 뜻입니다.

→ **교훈**: 완전 자동화 파이프라인의 현실적 기대치는 "절반은 버린다"입니다. 사람 리뷰 시간을 미리 예산에 넣으세요.

**② RL Engineering 팀 — 첫 시도 성공률 33%**
one-shot 구현이 성공하는 비율이 약 1/3입니다. 나머지는 사람이 유도해야 합니다. 디버깅·에러 조사는 *"mixed results"*라고 솔직하게 적혀 있습니다.

→ **교훈**: "한 번에 되겠지"로 일정을 짜면 안 됩니다. 3번 중 2번은 협업 모드로 전환됩니다.

**③ Project Vend — 상점 운영 실패**
Claude가 사내 상점을 자율 운영한 실험입니다. $15짜리 음료를 $100에 사겠다는 제안을 **거절**했고, 원가 이하로 가격을 매겼고, **존재하지 않는 결제 계정을 환각**했고, 할인 남발을 스스로 인지하고도 반복했으며, 발표한 가격 정책 개혁을 며칠 만에 스스로 폐기했습니다. 결과는 수익성 실패.

→ **교훈**: **경제적 판단과 장기 일관성**은 아직 맡기면 안 되는 영역입니다. 실수로부터 안정적으로 학습하지 못합니다.

**④ 2026년 3~4월 품질 저하 사태 (공식 포스트모템)**
약 6주간 "덜 똑똑해졌다"는 보고가 이어졌고, 원인은 세 가지였습니다 — 기본 reasoning effort를 낮춘 것(회사가 *"잘못된 트레이드오프"*라고 인정), 캐싱 버그로 대화 중 추론 이력이 계속 지워진 것, 응답 길이를 제한한 시스템 프롬프트 변경(광범위 테스트에서 품질 3% 하락 확인).

한 사용자의 논평이 핵심을 찌릅니다.

> *"인터랙티브 사용에서는 품질 저하가 명백합니다. 궤도를 수정할 수 있죠. **자동화 파이프라인에서는 세 단계 아래로 내려갈 때까지 조용합니다.**"*

→ **교훈**: 자동화할수록 **자체 점검 장치**가 필요합니다. 예약 작업에는 반드시 "결과가 이상하면 알려줘" 조항을 넣으세요.

## 2-2. 한국어권에서 반복 확인된 실패 (가장 실용적)

### 실패 ① 한도 소진 — 가장 흔한 좌절 지점

| 보고 | 상황 |
|---|---|
| PPT만 만들었는데 **슬라이드 20장에서 한도** (Pro) | 발표자료 제작 |
| 후속 글에서는 **10~12장에서 한도, 5시간 대기** | 발표자료 제작 |
| **Max 5($100) 플랜 4일 만에** 토큰 경고 | 코드 작업 |
| **Pro로 5시간 동안 프롬프트 2회** | 집단 보고 |

Anthropic 측 설명 중 실전에 바로 쓸 수 있는 것이 하나 있습니다.

> Claude Code는 메인 에이전트에 1시간 프롬프트 캐시 창을 씁니다. **컴퓨터를 1시간 이상 방치한 뒤 오래된 세션을 계속 쓰면 전체 캐시 미스가 자주 발생합니다.**

→ **오늘 바로 적용**: 자리를 오래 비웠으면 이어 쓰지 말고 **새 세션에서 핸드오프 문서로 시작**하세요(`F-03` → `F-04`). 비용과 품질이 동시에 좋아집니다.
→ **PPT는 나눠서**: 한 번에 10장 넘기지 마세요(`C-10`).

### 실패 ② 한글 문서 — 아직 구멍이 있습니다

| 문제 | 실제 우회법 |
|---|---|
| **HWP 파일을 못 읽음** | DOCX로 변환 후 처리. Pandoc으로 MD 변환. 또는 `pyhwpxlib` 같은 커뮤니티 라이브러리 |
| **PPT 한글 폰트·서식 깨짐** | 한 장 테스트로 폰트를 먼저 확정(`C-10`). 폰트를 이름으로 못 박기 |
| **차트가 편집 불가 이미지로 생성** | 데이터는 별도 엑셀로 받고 차트는 직접 삽입 |
| **터미널 한글 IME 밀림** (특히 Cursor 내장 터미널) | D2Coding·Noto Sans KR Mono 사용, UTF-8 확인, 다른 터미널 사용 |
| **기본 문체가 서술형** — 개조식 발표자료에 부적합 | 문체를 명시적으로 지시(아래 Before/After `#12`) |

→ **이암허브에 직접 해당**: 제안서가 한글(HWP) 산출물이므로 **입력은 DOCX로 통일**하는 규칙을 폴더 지침에 넣어두시는 것이 안전합니다.

### 실패 ③ 긴 세션에서 무너짐

- *"10턴 이상 대화 시 맥락 흐트러짐"*

# 제3부. Before / After 프롬프트 20선

같은 일을 시키는 두 문장인데 결과가 갈립니다. 왼쪽은 실제로 많이 쓰이는 표현이고, 오른쪽은 위 사례들에서 효과가 확인된 형태입니다. **오른쪽을 그대로 복사해 쓰시면 됩니다.**

## A. 문서·보고서

### #1 — 보고서 작성

**Before**
```
이 자료로 보고서 써줘.
```

**After**
```
[폴더]의 자료로 [주제] 보고서 초안을 만들어줘.

구성: ① 한 문장 결론 ② 근거 데이터 표 ③ 반복되는 이슈 ④ 다음 액션
분량: [ ]자 / 문체: 합쇼체, 개조식
숫자는 [원본 파일] 기준으로만 쓰고, 추정이 필요하면 '확인 필요'로 표시해.
자료 간에 서로 모순되는 내용이 있으면 본문에 넣지 말고 따로 모아줘.
```

**왜 갈리나** — 왼쪽은 완성도 판단을 Claude에게 맡깁니다. 오른쪽은 ①구성 ②분량·문체 ③숫자 근거 ④모순 처리까지 네 가지를 못 박아서, **결과물을 사람이 검사할 수 있는 형태**로 만듭니다. 마지막 줄이 특히 중요합니다 — 자료가 서로 충돌할 때 Claude는 보통 조용히 하나를 고릅니다.

---

### #2 — 회의록 정리

**Before**
```
회의록 요약해줘.
```

**After**
```
아래 회의록을 실행 체크리스트로 정리해줘. 목적은 이번 주에 바로 처리할 일을 찾는 것.

출력:
1. 한 문장 결론
2. 결정된 사항
3. 바로 할 일 (담당자·기한·산출물 3열 표)
4. 담당자나 일정이 확인되지 않은 항목
5. 다음 회의에서 물어볼 질문

회의록에 없는 담당자·기한·숫자는 추측하지 말고 '확인 필요'로 표시해.
```

**왜 갈리나** — "요약"은 목적이 없어서 무엇을 버릴지 판단할 수 없습니다. 오른쪽은 목적("이번 주에 할 일")을 주고, **4번 항목으로 '모르는 것'을 담을 자리를 만들어**줍니다. 이 자리가 없으면 Claude는 빈칸을 그럴듯하게 채웁니다.

---

### #3 — 긴 문서 읽히기

**Before**
```
(문서를 붙여넣고) 이거 어떻게 생각해?
```

**After**
```
(문서를 위에 먼저 붙여넣고, 질문은 아래에)

위 문서에서 [질문]과 관련된 문장을 원문 그대로 <quotes> 태그 안에 인용해줘.
그다음 그 인용문에만 근거해서 판단을 <analysis> 태그 안에 써줘.
문서에 답이 없으면 추론하지 말고 없다고 말해.
```

**왜 갈리나** — 두 가지가 다릅니다. 첫째, **긴 자료를 위에 두고 질문을 아래**에 둡니다(공식 테스트 기준 최대 30% 차이). 둘째, 인용을 먼저 뽑게 하면 지어내기가 급감합니다. 근거 문장이 없으면 판단을 쓸 수 없는 구조가 되기 때문입니다.

---

### #4 — 문서 여러 개 비교

**Before**
```
이 문서들 비교해줘.
```

**After**
```
이 폴더의 문서들을 읽고 다음 순서로 정리해줘.

1. 모든 문서가 공통으로 말하는 것
2. 문서마다 결론이 갈리는 지점 ← 이걸 '이견' 항목으로 따로 모아줘
3. 어느 문서에도 답이 없는 빈칸

각 항목에 근거 문서명과 해당 문장을 달아줘.
```

**왜 갈리나** — "비교"라고만 하면 공통점 위주로 뭉뚱그립니다. **실무에서 값어치 있는 정보는 2번(이견)과 3번(빈칸)**인데, 명시하지 않으면 나오지 않습니다.


**왜 갈리나** — 곧바로 분석시키면 **잘못된 질문에 정확하게 답한** 결과물을 받습니다. 데이터 구조를 먼저 확인하고 질문을 고르는 데 드는 1분이, 나중에 30분을 아낍니다.

```
- 시트3: 확인이 필요한 항목과 그 이유

수식이 들어간 셀 옆에 어떤 계산인지 설명 열을 추가해줘.
```

**왜 갈리나** — 값만 박힌 표는 원본이 바뀌면 쓸모없어집니다. **수식으로 넣으라고 명시**해야 살아 있는 시트가 나옵니다. 시트3(확인 필요)은 사람이 검증할 지점을 Claude가 스스로 표시하게 만드는 장치입니다.

### #7 — 숫자 검증

```
계산 맞는지 확인해줘.
```

**After**
```
보고서를 쓰기 전에 자기검증부터 해줘.
- 본문의 모든 수치를 원본 데이터에서 다시 계산해서 대조해줘
- 불일치가 하나라도 있으면 보고서를 쓰지 말고 먼저 알려줘
- 상관관계를 인과로 서술한 문장이 있는지 스스로 점검해줘

검증을 통과한 뒤에 보고서를 쓰고, 각 수치 옆에 산출 근거(파일·컬럼·집계 방식)를 달아줘.
```

**왜 갈리나** — "확인해줘"는 확인한 척으로 끝날 수 있습니다. 오른쪽은 **불일치가 있으면 다음 단계로 못 가게** 게이트를 걸었습니다. 컨설팅 보고서에서 가장 치명적인 사고가 수치 불일치라는 점을 생각하면, 이 한 문단이 문서 전체의 신뢰도를 지탱합니다.

# 제4부. 복붙 세팅 파일 3종

세 파일을 오늘 만들어 두면, 위 프롬프트 중 절반은 매번 안 써도 됩니다. **길이가 곧 품질입니다 — 짧게 유지하세요.** 어느 팀은 CLAUDE.md를 50줄 이하로 유지하며 "150줄부터 준수율이 깨진다"고 실측 보고했습니다.

## 4-1. Cowork 폴더 지침 — `CLAUDE.md`

연결한 작업 폴더 안에 이 이름으로 저장합니다. 문서 업무의 기본값이 됩니다.

```markdown
# 작업 규칙

## 안전
- 파일 삭제·이동·덮어쓰기 전에 목록을 보여주고 확인을 기다릴 것
- 삭제는 절대 자동 실행하지 말 것
- 원본은 덮어쓰지 말고 수정본에 _v2 접미사를 붙일 것

## 사실성
- 열어보지 않은 문서에 대해 추측하지 말 것. 파일을 먼저 읽고 답할 것
- 자료에 없는 수치·담당자·일정은 만들지 말고 '확인 필요'로 표시할 것
- 모든 수치에 출처(파일명·시트·행)를 병기할 것
- 자료 간 모순이 있으면 본문에 넣지 말고 '이견' 항목으로 분리할 것

## 완료 보고
- "완료했습니다"라고 쓰지 말 것
- 확인한 것 / 확인하지 못한 것 / 내가 직접 봐야 할 지점을 적을 것

## 산출물
- output/ 아래 YYYYMMDD_제목.확장자 로 저장
- 입력 문서는 DOCX 기준. HWP는 먼저 DOCX로 변환한 뒤 처리
- PPT는 한 번에 10장을 넘기지 말 것

## 문체
- 합쇼체 / 개조식(항목은 '~함, ~임'으로 종결) / 한 항목 최대 2줄
- 과장 표현 금지: 혁신적, 극대화, 최적의, 완벽한

## 압축
- 압축할 때 수정한 파일 목록과 확정된 결정사항은 항상 보존할 것
```

> **왜 이 순서인가** — 위에서부터 사고 위험이 큰 순입니다. 지침이 길어지면 뒷부분부터 무시되므로, 잃으면 안 되는 것을 먼저 둡니다.

## 4-2. Chat Projects 지침

Claude 웹/앱의 프로젝트 설정에 넣습니다. **짧게 유지하는 것이 핵심**입니다 — 말투·독자·형식·금지 네 가지만.

```
당신은 농업·스마트팜 분야 사업 문서를 다루는 전문 에디터입니다.

독자: [주관기관 심사위원 / 농가 / 내부 경영진] 중 해당하는 쪽
문체: 합쇼체. 한 문단 3~5문장. 소제목은 ### 사용
금지: 과장 표현(혁신적, 극대화, 최적의), 원문에 없는 수치 생성, 근거 없는 단정

작업 원칙
- 자료에 없는 내용은 '확인 필요'로 표시하고 절대 채워 넣지 않습니다
- 결론을 먼저 쓰고 근거를 뒤에 붙입니다
- 요청 범위만 다루고, 시키지 않은 개선 제안은 마지막에 한 줄로만 언급합니다
- 답변 전에 목적과 독자가 불명확하면 먼저 물어봅니다
```

## 4-3. Claude Code용 `CLAUDE.md`

저장소 루트에 둡니다. **판별 질문은 하나** — "이 줄을 지우면 Claude가 실수할까?" 아니면 지웁니다.

```markdown
# 프로젝트
[한 줄 설명] · 스택: [ ]

## 명령어
- [개발 서버 실행 명령]
- [테스트 실행 명령]
- [린트·타입체크 명령]

## 절대 규칙
- 요청한 범위만 손댈 것. 인접 코드를 "개선"하지 말 것
- 테스트를 지우거나 skip으로 바꿔서 통과시키지 말 것
- .env 파일을 커밋하지 말 것
- main에 직접 push하지 말 것

## 작업 방식
- 3개 이상 파일을 건드리는 변경은 계획을 먼저 제시할 것
- 변경 후 테스트를 실행하고, 결과 출력을 그대로 보여줄 것
- 판단이 갈리면 조용히 하나를 고르지 말고 선택지를 제시할 것
- 축약어는 풀어서 설명할 것
- 반복 작업은 직접 하지 말고 스크립트로 만들어 재사용할 것

## 손대지 말 것
- [마이그레이션 폴더]
- [인증·결제 관련 파일 — 변경 시 반드시 리뷰]

## 압축
- 압축할 때 수정한 파일 전체 목록과 테스트 명령어는 항상 보존할 것
```

> 마지막 두 항목("축약어는 풀어서", "반복 작업은 스크립트로")은 컬리 개발팀이 사내 공통 규칙으로 배포한 문장을 그대로 가져온 것입니다.

## 4-4. 세 파일의 관계

```
Chat Projects 지침   →  발상·기획 단계의 말투와 판단 기준
Cowork 폴더 지침     →  파일을 만지는 모든 작업의 안전선
Code CLAUDE.md       →  코드를 고치는 모든 작업의 경계선
```

세 곳에 **공통으로 들어가야 하는 세 줄**이 있습니다. 다른 건 다 빼도 이건 남기세요.

```
- 열어보지 않은 것에 대해 추측하지 마
- 자료에 없는 것은 만들지 말고 '확인 필요'로 표시해
- "완료했습니다" 대신 확인한 것과 확인하지 못한 것을 적어
```

# 제5부. 업무 워크스루 — 처음부터 끝까지

각 워크스루는 **프롬프트를 순서대로 복사해 쓰면 되도록** 구성했습니다. 대괄호만 채우세요.

## 5-1. 정성제안서 (PPT → 한글 제안서)

**전제**: 발표자료 PPT가 있고, 주관기관 RFP가 있습니다. `ppt-to-hwp-proposal` 스킬을 함께 씁니다.

### [0단계] RFP 해부 — 여기서 승부가 납니다

```
첨부한 제안요청서를 분석해줘. 아직 제안서는 쓰지 마.

다음만 뽑아줘.
1. 요구 목차 — RFP가 명시한 순서 그대로. 번호 체계까지 원문대로
2. 평가 항목과 배점 — 배점이 큰 순으로 정렬
3. 필수 제출 서류와 양식 제약 (분량, 서식, 파일 형식)
4. 반드시 답해야 하는 요구사항을 문장 단위로 추출 → 체크리스트로
5. 애매해서 발주처에 질의해야 할 항목

RFP에 없는 내용은 추측해서 채우지 마. 각 항목에 RFP의 해당 위치(쪽·조항)를 달아줘.

결과를 RFP_체크리스트.md 로 저장해줘.
```

> **왜 이게 0단계인가** — 제안서는 "잘 썼는가"보다 **"요구항목을 빠뜨리지 않았는가"**에서 떨어집니다. 4번 체크리스트가 마지막 검증의 기준 문서가 됩니다.

### [1단계] 목차 도출

```
RFP_체크리스트.md 의 요구 목차에 맞춰, 첨부한 PPT의 내용을 어느 항목에 배치할지 매핑표를 만들어줘.

3열로: [RFP 요구 항목] | [대응할 PPT 슬라이드] | [부족한 내용]

PPT에 대응 내용이 없는 항목은 빈칸으로 두고 '자료 필요'로 표시해. 지어내지 마.
아직 본문은 쓰지 마.
```

여기서 **'자료 필요' 목록이 곧 오늘 챙겨야 할 일**입니다. 이 단계를 건너뛰면 제안서를 다 쓴 뒤에 빈 곳을 발견합니다.

### [2단계] 본문 작성

```
매핑표대로 본문을 작성해줘. (ppt-to-hwp-proposal 스킬 적용)

- 개조식으로 풀어 쓸 것 (항목은 '~함, ~임' 종결, 한 항목 최대 2줄)
- PPT의 그림, 특히 추진일정표와 조직도는 해당 본문 아래에 그대로 삽입
- 실적·인력·기간 수치는 PPT 원본 기준으로만 쓸 것
- PPT에 없는 수치가 필요하면 '확인 필요'로 표시하고 넘어갈 것
- 과장 표현 금지

한 번에 다 쓰지 말고, RFP 목차의 대항목 단위로 끊어서 보여줘.
```

### [3단계] 레드팀 검증 — **새 대화에서**

```
(새 대화를 열고 제안서 초안과 RFP_체크리스트.md 만 붙여넣는다)

이 제안서를 RFP 체크리스트에 대조해서 검토해줘.

- 체크리스트의 각 요구사항이 실제로 답변됐는가 (항목별 O/X/부분)
- 배점이 큰 평가항목에 분량과 근거가 배분됐는가
- 근거 없이 단정한 문장이 있는가
- RFP가 요구하지 않은 내용으로 분량을 채운 곳이 있는가

스타일 취향이 아니라 '빠진 것'만 보고해.
정확성이나 명시된 요구사항에 영향을 주는 문제만 지적해.
```

마지막 두 줄을 빼지 마세요. 없으면 없는 문제를 만들어 옵니다.

### [4단계] 최종 점검

```
제안서에 들어간 모든 수치(실적, 인력, 기간, 금액)를 원본 자료에서 다시 확인해서 대조표를 만들어줘.
불일치가 하나라도 있으면 목록으로 먼저 보여주고, 수정은 내 지시를 기다려.
'확인 필요'로 남아 있는 항목도 함께 목록으로 뽑아줘.
```

## 5-2. 스마트팜 경영성과 컨설팅 보고서

**전제**: 농진청 소득조사표, 생육·환경·출하 데이터가 있습니다. `smartfarm-consulting-report` 스킬을 함께 씁니다.

핵심 원칙은 컬리 팀의 결론과 같습니다 — **수집·집계는 스크립트로, 해석·처방은 Claude로.**

### [1단계] 수집 — 데이터를 대화에 쏟지 않기

```
[폴더]의 데이터를 raw/ 로 정리해줘. 내용을 대화에 출력하지 마.

다음만 보고해줘.
- 파일별 행/열 수
- 컬럼명과 각 컬럼 샘플 3개
- 결측·이상 의심 지점 (예: 단수가 0이거나 비정상적으로 큰 행)
- 농가별·기간별 데이터가 누락된 구간
```

> 이 한 줄("내용을 대화에 출력하지 마")이 비용과 품질을 동시에 지킵니다. 컬리 팀은 이걸 몰라서 *"2~3일치만 수집해도 비용과 속도가 급격히 악화"*되는 문제를 겪었습니다.

### [2단계] 정제 — 버린 데이터를 남기기

```
raw/ 를 정제해서 clean/ 을 만들어줘.

- 전체를 읽지 말고 샘플로 파악한 뒤 정제 스크립트(cleaning.py)를 작성해서 실행해
- 정제 규칙마다 몇 행이 영향받았는지 로그를 남겨줘
- 데이터를 조용히 버리지 마. 제외한 행은 dropped.csv 로 따로 저장하고 제외 사유를 열로 붙여줘

정제 전후 행 수 대조표를 먼저 보여줘. 내가 승인하면 다음 단계로 가자.
```

### [3단계] 분석 — 질문을 먼저 고르기

```
clean/ 데이터로 답할 수 있는 질문을 5개 제안해줘. 아직 분석하지 마.

각 질문마다:
- 어떤 컬럼을 쓰는지
- 이 질문에 답하려면 데이터가 충분한지
- 답이 나와도 단정할 수 없는 부분은 무엇인지

내가 3개를 고르면 그것만 분석해줘.
```

### [4단계] 시각화

```
고른 질문만 시각화해줘. 차트마다 세 줄을 붙여줘.
- 이 차트가 보여주는 것
- 이 차트가 보여주지 '않는' 것
- 이 차트로 내리면 안 되는 결론

비교 대상(전년, 지역 평균, 상위 농가)이 데이터에 없으면 만들지 말고 '비교군 없음'으로 표시해.
```

### [5단계] 보고서 — 검증 게이트를 먼저

```
보고서를 쓰기 전에 자기검증부터 해줘.
- 본문에 들어갈 모든 수치를 clean/ 에서 다시 계산해 대조해줘
- 불일치가 하나라도 있으면 보고서를 쓰지 말고 먼저 알려줘
- 상관관계를 인과로 서술한 문장이 있는지 스스로 점검해줘

검증을 통과하면 smartfarm-consulting-report 스킬로 보고서를 작성해줘.
각 수치 옆에 산출 근거(파일·컬럼·집계 방식)를 달고,
개선처방은 데이터로 뒷받침되는 것만 쓰고 나머지는 '추가 조사 필요'로 분리해줘.
```

### [6단계] 교차검증 (선택)

```
(새 대화에서) 이 보고서를 검토해줘.
- 데이터가 뒷받침하지 않는 처방이 있는가
- 농가가 실제로 실행할 수 없는 제안이 있는가 (비용·설비·인력 제약)
- 상관을 인과로 말한 문장

정확성에 영향을 주는 문제만 지적해.
```

## 5-3. IPinsight — 기술사업화 서비스

**전제**: 기술사업화 지원 업무(특허·기술 분석 → 시장성 평가 → 사업화 전략 → 수요처 매칭 → 보고서)를 가정하고 구성했습니다. 실제 서비스 범위와 다른 부분은 대괄호를 조정해서 쓰시면 됩니다.

이 업무는 **환각이 가장 위험한 영역**입니다. 특허번호, 시장 규모, 경쟁사 실적은 전부 그럴듯하게 지어낼 수 있는 형태이고, 앞서 본 "세상에 없는 논문" 사례가 정확히 이 유형입니다. 그래서 워크스루 전체에 근거 추적 장치를 깔았습니다.

### [0단계] 스코핑 — 무엇을 판단하려는 조사인가

```
[기술명 / 특허번호]에 대한 기술사업화 검토를 하려고 해. 조사 시작 전에 나를 인터뷰해줘.

물어봐야 할 것: 이 검토의 의사결정 목적(이전? 출자? 창업? 수요처 매칭?), 보고 대상,
검토 기한, 이미 확보한 자료, 제외할 영역, 신뢰할 출처의 기준.

뻔한 질문은 하지 말고, 내가 미처 생각 못 했을 지점을 파고들어.
끝나면 IP_BRIEF.md 로 저장해줘.
```

### [1단계] 기술 이해 — 원문에서만

```
IP_BRIEF.md 를 기준으로 [특허/기술 자료]를 분석해줘.

1. 청구항 기반 핵심 기술 요지 — 청구항 번호를 인용하며
2. 기술적 차별점 — 명세서에 실제로 적힌 것만
3. 적용 가능 분야 — 명세서에 언급된 것과, 내가 추론한 것을 반드시 구분해서 표시
4. 기술 성숙도(TRL) 판단과 그 근거
5. 자료만으로는 판단할 수 없는 항목

명세서에 없는 내용을 아는 것처럼 쓰지 마. 추론은 [추론]으로 표시해.
```

> 3번의 "명세서에 적힌 것 / 내가 추론한 것 구분"이 이 단계의 전부입니다. 기술사업화 보고서가 무너지는 지점이 대개 여기입니다.

### [2단계] 시장·경쟁 조사 — 축을 나누고 경계를 긋기

```
[기술 분야]의 시장을 조사할 거야. 조사 축을 4개로 나눠서 각각 따로 진행해줘.
축끼리 내용이 겹치면 안 돼.

축1 — 시장 규모와 성장률 (반드시 출처 기관명·발표연도·원문 링크를 함께)
축2 — 경쟁 기술·대체 기술
축3 — 국내외 주요 플레이어와 최근 동향
축4 — 규제·인증·표준 요건

규칙:
- 모든 수치에 출처 URL과 확인 일자를 달 것
- 출처를 찾지 못한 수치는 쓰지 말 것. '출처 미확인'으로 남겨둘 것
- 2차 인용(누가 인용한 것을 재인용)은 그렇다고 표시할 것
- 추정치와 실측치를 구분할 것

원자료는 findings.md 에 누적하고, 대화에는 요약만 보여줘.
```

### [3단계] 근거 검증 — 이 단계를 건너뛰지 마세요

```
findings.md 의 모든 수치·주장에 대해 검증표를 만들어줘.

각 항목마다 4열로:
[주장] | [출처] | [출처 등급: 1차/2차/미확인] | [반대 근거 존재 여부]

그다음 다음 세 가지를 따로 뽑아줘.
1. 출처가 1개뿐인 주장
2. 출처가 2차 인용뿐인 주장
3. 서로 모순되는 자료

이 셋은 보고서 본문에 단정문으로 쓰지 않을 거야.
```

> 앞서 본 팩트체크 사례에서 뉴스레터 1건의 클레임 12건 중 **7건이 실제 문제**였습니다. 시장 데이터는 그보다 더 위험합니다.

### [4단계] 사업화 전략

```
IP_BRIEF.md 의 의사결정 목적에 맞춰 사업화 방안을 제시해줘.

- 옵션을 3개 이상 제시하고, 각각 전제 조건·필요 자원·회수 기간·리스크를 병기
- 하나를 추천하되, 왜 나머지를 배제했는지도 쓸 것
- 3단계 검증표에서 '근거 약함'으로 분류된 항목에 의존하는 판단은 그렇다고 명시할 것
- 실행 주체(기술보유자/수요기업/우리)를 각 액션마다 표시할 것

내가 모르는 리스크를 찾아내는 게 이 단계의 목적이야. 낙관적으로 쓰지 마.
```

### [5단계] 수요처 매칭 (해당 시)

```
[기술]의 잠재 수요기업 후보를 찾아줘.

각 후보마다: 기업명 / 매칭 근거(어떤 사업·제품과 연결되는지) / 근거 출처 URL /
접촉 우선순위와 그 이유 / 매칭이 어려울 수 있는 이유

규칙:
- 홈페이지·공시·보도자료에서 확인되는 사실만 쓸 것
- 확인되지 않은 사업 계획이나 수요를 추정해서 쓰지 말 것
- 확인 못 한 항목은 빈칸으로 두고 '확인 필요'로 표시할 것
```

### [6단계] 보고서 + 최종 레드팀

```
[보고서 작성]
검증을 통과한 내용만으로 보고서를 작성해줘.
- 모든 수치에 출처와 확인 일자를 각주로
- 3단계에서 '근거 약함'으로 분류된 항목은 단정문 대신 '~로 추정됨(출처 1건)'으로 표기
- 마지막에 '추가 확인이 필요한 항목' 절을 반드시 넣을 것

[레드팀 — 새 대화에서]
이 기술사업화 보고서를 IP_BRIEF.md 와 검증표에 대조해 검토해줘.
- 원래 의사결정 목적에 답하고 있는가
- 검증표에서 '근거 약함'이던 항목이 본문에서 단정문이 됐는가  ← 가장 중요
- 출처 없이 등장한 수치가 있는가
- 반대 입장(투자 거절, 이전 무산)이 제기할 가장 강한 반론은 무엇인가

스타일이 아니라 갭만 보고해.
```

### 이 업무를 스킬로 굳히려면

3~4회 돌려보고 나면 규칙이 정리됩니다. 그때 이렇게 하세요.

```
지금까지 IPinsight 검토를 진행한 과정을 스킬로 만들어줘.

포함할 것:
1. 이 스킬이 하는 일 (한 문장)
2. 언제 발동해야 하는지 — 내가 쓸 법한 표현 5개 ("기술사업화 검토", "특허 시장성 분석" 등)
3. 반드시 지켜야 할 규칙 — 특히 출처 등급 구분과 '근거 약함' 표기
4. 단계별 산출물 이름과 저장 위치
5. 내가 중간에 수정 요청했던 것들을 '흔한 실수' 항목으로

본문은 500줄을 넘기지 말고, 상세 기준은 참조 파일로 분리해줘.
```

> 논문 메타분석 사례의 결론이 여기에도 적용됩니다 — *"SKILL.md 설계가 성능의 80%"*. 그리고 **손으로 3회 완주하기 전에는 스킬을 만들지 마세요.** 규칙이 어디서 튀어나오는지 모르는 채로 만든 스킬은 거의 실패합니다.

# 제6부. 한 장 체크리스트

인쇄해서 옆에 두고 쓰는 용도입니다. 별도 HTML 파일로도 드렸습니다.

## 시작 전 (30초)

- [ ] 목적과 독자를 한 문장으로 말할 수 있는가? 없으면 **먼저 인터뷰시킨다** (`#15`)
- [ ] 자료를 폴더에 모아뒀는가? 대화 중에 하나씩 붙여넣지 않는다
- [ ] 출력 형식을 정했는가? (항목 구성·분량·문체·파일 형식)
- [ ] **이 결과가 틀렸는지 어떻게 확인할 것인가?** ← 답이 없으면 아직 시작하지 마라

## 프롬프트를 쓸 때

- [ ] 긴 자료는 **위**, 질문은 **아래**
- [ ] "요약해줘" 대신 **무엇을 위한 요약인지** 목적을 준다
- [ ] '모르는 것'을 담을 자리를 만든다 → "확인 필요 항목" 절
- [ ] 금지가 아니라 지시로 쓴다 ("불릿 쓰지 마" → "완결된 문단으로 써줘")
- [ ] 되돌리기 어려운 작업이면 **계획을 먼저 보여달라**고 한다

## 작업 중

- [ ] 대량 반복은 **2~3건 먼저** 검증하고 확대한다
- [ ] PPT는 **한 장 테스트 → 5장 → 5장**
- [ ] 같은 지적을 **두 번** 했으면 세 번째는 고치지 말고 **새 대화**로 (`#16`)
- [ ] 10턴이 넘어가면 맥락이 흐트러진다고 가정한다
- [ ] 압축할 때는 **보존할 것을 명시**한다

## 끝낼 때

- [ ] "완료했습니다" 대신 **확인한 것 / 못 한 것**을 받는다 (`#19`)
- [ ] 모든 수치를 **원본에서 재계산해 대조**시킨다 (`#7`)
- [ ] 최종 검토는 **새 대화**에서, "빠진 것만 보고해" (`#20`)
- [ ] 내일 이어갈 일이면 **인수인계 문서**를 쓰게 한다 (`#17`)
- [ ] 같은 일을 또 할 것 같으면 → 지침 파일에 한 줄 추가 (3회 이상이면 스킬로)

## 비용을 아끼는 다섯 가지

- [ ] 자리를 오래 비웠으면 이어 쓰지 말고 **새 대화 + 인수인계 문서**
- [ ] 데이터는 "대화에 출력하지 마"라고 지시한다
- [ ] 수집·집계는 **스크립트로**, 해석·판단만 Claude에게
- [ ] 반복 지시는 지침 파일로 내려서 매번 안 쓴다
- [ ] 무거운 작업 전에 가벼운 잡담으로 컨텍스트를 채우지 않는다

## 위험 신호 — 이게 보이면 멈춘다

| 신호 | 대응 |
|---|---|
| 출처 없는 수치가 등장 | `A-22` + 검증표로 되돌린다 |
| "아마", "일반적으로"가 늘어남 | 자료가 부족한 것. 자료를 더 주거나 범위를 좁힌다 |
| 같은 실수를 세 번째 반복 | **새 대화**. 고치지 마라 |
| 시키지 않은 것까지 고쳐옴 | "요청한 범위만" 지시를 지침 파일에 |
| 답변이 갑자기 짧고 성의 없어짐 | 컨텍스트가 찼다. 인수인계 후 새 대화 |
| 파일을 안 읽고 답함 | "파일을 먼저 읽고 답해" |
