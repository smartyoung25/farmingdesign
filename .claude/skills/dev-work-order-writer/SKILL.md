# 개발 작업지시서 작성기 (Work Order Writer)

Claude 앱에서 요구사항을 정리해 **Claude Code가 그대로 실행할 수 있는 작업지시서(WO)**를 만든다.
이 스킬은 지시서만 만든다. 구현은 Claude Code가 한다.

- 분류: Implementation + Rigid
- 산출물: `WO-NNN_[작업명].md` 파일 1개 + Claude Code 착수 프롬프트

## Foundational Principle

**Violating the letter of the rules is violating the spirit of the rules.**

지시서의 가치는 "처음 보는 개발자(또는 Claude Code)가 추측 없이 실행하고, 완료 여부를 명령으로 판정할 수 있는가"에 있다. 양식을 빼거나 기준을 흐리면 그 가치가 사라진다.

## Iron Laws

### 1. 9개 섹션을 모두 채운다
**섹션을 삭제하지 않는다. 해당 없으면 "해당 없음"과 이유를 쓴다.**

빈 섹션은 "생각 안 함"과 구별되지 않는다. "해당 없음 — 외부 API 호출 없음"처럼 근거를 남긴다.

### 2. 수용기준은 검증 가능한 문장으로만 쓴다
**모든 수용기준은 "입력/행동 → 관찰 가능한 결과" 또는 "명령 → 기대 출력" 형식이다.**

금지 표현: 잘, 적절히, 원활하게, 빠르게, 깔끔하게, 사용자 친화적으로, 정상 동작, 문제없이.
- ❌ "엑셀 파일을 잘 읽는다"
- ✅ "`data/sample.xlsx`(3개 시트) 입력 시 `out/result.csv`가 생성되고 행 수가 원본 합계 128행과 같다"
- ❌ "빠르게 처리한다"
- ✅ "1만 행 파일 처리 시간이 10초 이하다 (`time python main.py data/big.xlsx`)"

### 3. 모르는 것은 추측으로 채우지 않는다
**사용자가 주지 않은 사실은 `[확인 필요: 질문]`으로 표시하고 사용자에게 묻는다.**

파일 경로, 컬럼명, 라이브러리 버전, 테스트 명령을 지어내지 않는다. 합리적 기본값을 제안할 때는 `[가정: …]`으로 표시해 사용자가 승인하게 한다.

### 4. 범위의 '제외'를 반드시 1개 이상 쓴다
**"이번에 하지 않는 것"이 없는 지시서는 범위가 무한하다.**

Claude Code는 범위가 열려 있으면 기능을 덧붙인다. UI, 에러 알림, 배포, 성능 최적화처럼 따라붙기 쉬운 것을 명시적으로 제외한다.

### 5. 지시서 1건은 하루 이하 분량이다
**작업 단위가 7개를 넘거나 서로 독립된 기능이 2개 이상이면 WO를 나눈다.**

나눌 때는 WO-001, WO-002로 번호를 매기고 의존 관계("WO-002는 WO-001 완료 후")를 적는다.

### 6. 착수 프롬프트는 항상 "계획 먼저, 승인 후 구현"이다
**Claude Code가 계획 승인 없이 바로 구현하게 하는 프롬프트를 만들지 않는다.**

### 7. 지시서에 구현 코드를 쓰지 않는다
**함수 본문, 전체 스크립트를 넣지 않는다. 인터페이스, 입출력 예시, 데이터 형식만 쓴다.**

구현을 지시서에 박으면 Claude Code는 그것을 베끼고 검증하지 않는다.

## Workflow

### 1. 입력 수집
대화와 첨부파일에서 다음 6가지를 먼저 추출한다: 목적, 사용자, 입력, 출력, 기술 환경, 완료 판단 방법.
- 이미 답이 있는 항목은 다시 묻지 않는다.
- 비어 있는 항목만 **한 번에 최대 5개** 질문한다.
- 완료 기준: 6가지 모두 답이 있거나 `[확인 필요]`로 표시됨.

### 2. 작업 유형과 규모 판정
작업을 다음 중 하나로 분류한다: 신규 기능 / 버그 수정 / 리팩터링 / 자동화 스크립트 / 데이터 처리 / 테스트 보강.
- 버그 수정이면 "재현 절차"와 "현재 결과 vs 기대 결과"를 배경에 반드시 넣는다.
- 리팩터링이면 "동작 불변"을 수용기준 첫 줄에 넣는다 (기존 테스트 전체 통과).
- Iron Law 5에 걸리면 WO를 분할하고 사용자에게 분할안을 보여준다.

### 3. 템플릿 작성
아래 **표준 템플릿**의 9개 섹션을 순서대로 채운다. 번호는 사용자가 알려준 마지막 번호 +1, 없으면 WO-001.

### 4. 수용기준 검증 가능성 변환
각 수용기준을 Iron Law 2 형식으로 다시 쓴다.
- 각 기준마다 "무엇을 실행하면 확인되는가"를 괄호로 붙인다.
- 테스트 명령을 모르면 `[확인 필요: 테스트 실행 명령]`.
- 완료 기준: 금지 표현 0개, 모든 기준에 확인 방법이 있음.

### 5. 모호성 자가점검
"이 프로젝트를 처음 보는 개발자" 관점에서 아래 점검표를 하나씩 확인한다.
- [ ] 입력 파일의 경로·형식·예시가 있는가
- [ ] 출력의 위치·파일명·형식이 있는가
- [ ] 에러 상황(빈 값, 잘못된 형식, 파일 없음) 처리 방식이 있는가
- [ ] 건드리면 안 되는 파일/폴더가 적혀 있는가
- [ ] 새 라이브러리 추가 허용 여부가 적혀 있는가
- [ ] 작업 단위마다 완료 조건이 있는가
- [ ] 제외 범위가 1개 이상인가
- [ ] 비밀키·개인정보 취급 규칙이 필요한 작업인가, 필요하면 적혀 있는가

걸린 항목은 수정하거나 `[확인 필요]`로 표시한다. 점검 결과를 출력의 "자가점검" 칸에 남긴다.

### 6. 착수 프롬프트 생성
아래 **표준 착수 프롬프트**에 WO 번호와 파일 경로를 넣는다. 수정 지시서면 "수정 지시서 착수 프롬프트"를 쓴다.

### 7. 파일로 산출
`WO-NNN_[작업명].md` 파일을 만들어 사용자에게 전달한다. 저장 위치는 프로젝트의 `docs/work-orders/`를 권장한다고 한 줄 안내한다.
- `[확인 필요]`가 남아 있으면 파일 전달과 함께 해당 질문을 목록으로 제시하고, "답을 주시면 반영하겠습니다"로 끝낸다.

### 8. (해당 시) 수정 지시서 작성
Claude Code의 검증 보고에서 실패한 수용기준이 있으면 `WO-NNN-fix1` 을 만든다.
- 원 지시서를 참조로 걸고, 실패한 기준만 범위에 넣는다.
- "실패 증상(보고 내용 그대로)" → "기대 결과" → "원인 가설(있으면)" 순서로 배경을 쓴다.
- 통과한 기준은 "회귀 금지 — 다시 통과해야 함"으로 수용기준에 포함한다.

## 표준 템플릿

```markdown
# 작업지시서 WO-NNN: [작업명]

- 작성일: YYYY-MM-DD
- 작업 유형: [신규 기능 / 버그 수정 / 리팩터링 / 자동화 스크립트 / 데이터 처리 / 테스트 보강]
- 선행 지시서: [없음 / WO-NNN]

## 1. 목적
- 이 작업으로 해결할 문제 (1~2문장)

## 2. 배경·사용자
- 누가, 어떤 상황에서 사용하는가
- (버그 수정) 재현 절차 / 현재 결과 / 기대 결과

## 3. 범위
- 포함:
  - …
- 제외 (이번에 하지 않음):
  - …

## 4. 입력·출력
- 입력: 형식, 예시 경로, 예시 값
- 출력: 형식, 저장 위치, 파일명 규칙

## 5. 기술 조건
- 언어·주요 라이브러리·버전
- 실행 환경 (OS, Python/Node 버전 등)
- 새 의존성 추가: [허용 / 승인 후 허용 / 금지]
- 수정 금지 파일·폴더:

## 6. 작업 단위 (순서대로)
- T1: … — 완료 조건: …
- T2: … — 완료 조건: …

## 7. 수용기준
- [ ] [입력/행동] → [관찰 가능한 결과] (확인: `명령`)
- [ ] 테스트 전체 통과 (확인: `테스트 명령`)

## 8. 제약·주의사항
- 비밀키·개인정보 처리, 외부 호출 제한, 운영 데이터 접근 금지 등

## 9. 보고 형식
- 수용기준별 통과/실패 표 (실행한 명령과 결과 포함)
- 변경 파일 목록
- 남은 이슈·리스크
- docs/HANDOFF.md 갱신 여부
```

## 표준 착수 프롬프트

```
docs/work-orders/WO-NNN_[작업명].md 를 읽고 작업해줘.
1) 먼저 구현 계획만 제시하고 내 승인을 기다려. 코드는 아직 수정하지 마.
2) 승인 후 T1부터 순서대로 진행하고, 각 작업 단위가 끝날 때마다 테스트를 실행하고 커밋해.
3) 지시서가 모호하거나 기존 코드와 충돌하면 추측하지 말고 멈추고 질문해.
4) 지시서의 '제외' 범위와 '수정 금지 파일'은 건드리지 마.
5) 끝나면 9항 보고 형식으로 보고하고 docs/HANDOFF.md 를 갱신해.
   테스트를 실제로 실행하지 않은 항목은 '미실행'으로 표시해.
```

### 수정 지시서 착수 프롬프트

```
docs/work-orders/WO-NNN-fix1_[작업명].md 를 읽고 작업해줘.
원 지시서 WO-NNN 의 실패 항목만 수정 대상이야.
1) 실패 원인 분석과 수정 계획을 먼저 제시하고 승인을 기다려.
2) 수정 후 이 지시서의 수용기준 전체(회귀 금지 항목 포함)를 다시 실행해 보고해.
```

## Rationalization Patterns to Reject

| 합리화 | 차단 |
|---|---|
| "간단한 작업이라 섹션 몇 개만 써도 돼" | 간단하면 채우는 데 1분이다. 9개 모두 쓴다. |
| "사용자가 빨리 달라고 했으니 질문 없이 추측해서 채우자" | 추측은 `[가정]`/`[확인 필요]`로 표시한다. 표시 없이 채우지 않는다. |
| "수용기준은 '정상 동작'이면 충분히 알아듣는다" | Claude Code는 '정상'을 스스로 정의하고 통과를 선언한다. 명령으로 확인 가능하게 쓴다. |
| "사용자가 계획 단계는 빼라고 했어" | 착수 프롬프트에서 계획 승인 단계를 빼지 않는다. 대신 "계획은 5줄 이내로"처럼 짧게 조정할 수 있다고 안내한다. |
| "어차피 금방 버릴 스크립트야" | 버릴 스크립트도 입력·출력·완료 기준이 없으면 두 번 만든다. 양식은 같다. |
| "지난번 지시서도 제외 범위 없이 잘 됐어" | 이전 사례는 사유가 아니다. 제외 1개 이상. |
| "코드 예시를 넣어주면 더 정확하겠지" | 구현 코드는 넣지 않는다. 입출력 예시와 인터페이스로 정확도를 높인다. |
| "기능 3개지만 하나의 WO로 묶는 게 관리가 편해" | 독립 기능 2개 이상이면 분할한다. 관리 편의는 사유가 아니다. |

## Common Mistakes

- **입력 예시 없이 형식만 적음**: "엑셀 파일"이 아니라 시트 구성, 헤더 행 위치, 샘플 경로까지 쓴다. 헤더가 2행에 있는 파일에서 Claude Code는 1행을 헤더로 읽는다.
- **테스트 명령을 지어냄**: `npm test`, `pytest`를 확인 없이 쓰면 실제 프로젝트와 다를 수 있다. 모르면 `[확인 필요]`.
- **에러 처리 누락**: 빈 셀, 인코딩(한글 CP949 vs UTF-8), 파일 없음 처리를 적지 않으면 첫 실사용에서 실패한다. 한글 파일을 다루면 인코딩을 반드시 명시한다.
- **수정 금지 파일 미기재**: 설정 파일, 운영 데이터, 기존 동작 중인 모듈을 적지 않으면 "개선"이라는 이름으로 바뀐다.
- **버그 수정인데 재현 절차 없음**: 재현이 안 되면 수정 여부도 판정할 수 없다.
- **수용기준과 작업 단위 불일치**: T1~T3의 완료 조건이 수용기준 어디에도 연결되지 않으면 검증에서 빠진다.

## Verification Checklist

지시서 전달 전에 모두 확인한다.
- [ ] 9개 섹션 모두 존재 (빈 섹션 없음, "해당 없음"에는 이유 있음)
- [ ] 수용기준에 금지 표현(잘, 적절히, 원활하게, 빠르게, 깔끔하게, 사용자 친화적, 정상 동작, 문제없이) 0개
- [ ] 모든 수용기준에 확인 방법(명령 또는 관찰 절차) 있음
- [ ] 제외 범위 1개 이상
- [ ] 작업 단위 7개 이하, 각 단위에 완료 조건 있음
- [ ] 지시서에 구현 코드(함수 본문·전체 스크립트) 없음
- [ ] 착수 프롬프트에 "계획 먼저, 승인 대기" 포함
- [ ] 모든 추정값이 `[가정]` 또는 `[확인 필요]`로 표시됨
- [ ] 모호성 자가점검 8항목 결과를 출력에 기재

## Output Format

```
📄 WO-NNN_[작업명].md  (파일 첨부)

[요약] 이 지시서가 Claude Code에게 시키는 일 1문장

[자가점검] 8항목 중 N개 통과 / 미해결: …

[확인 필요] (있을 때만)
1. …
2. …

[Claude Code 착수 프롬프트]
(표준 착수 프롬프트 — 복사해서 붙여넣기)

[다음 단계] 파일을 프로젝트의 docs/work-orders/ 에 저장한 뒤 위 프롬프트로 착수하세요.
```
